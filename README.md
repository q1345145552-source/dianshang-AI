# 电商作图平台 - 基础架子

现在有注册、登录、退出，还有工作台的页面保护。其余业务功能还没做，没有余额，没有项目，没有生成。

## 这里面有什么

三块应用。

web 是给客户看的网站，Next.js 写的。
api 是管业务的服务器，NestJS 写的，有一个健康检查接口。
worker 是在后面干活的进程，这轮只启动待命，不处理任何任务。

三个基础设施，都是真跑起来的，不是写在纸上的。

postgres 是数据库。
redis 是队列。
minio 是文件存储，存图片视频这类文件用。

## 注册

现在有注册了。注册页在 /register，登录页 /login 上有入口点过去。

要填三样：邮箱、密码、再输一遍密码。填完提交就注册成功，自动进工作台，工作台上显示自己的邮箱。

这几个情况会在提交之前就拦住，并且说清是哪里不对。

邮箱写得不像邮箱。
两次输入的密码不一样。
密码太短，少于 8 位。
密码太简单，只有数字或者只有字母。

拦是前后端各拦一次。浏览器里先拦一道，不合格连请求都不发。后端再独立查一遍，不指望浏览器。

邮箱已经注册过的话，会提示一句让人直接去登录。

密码规则是至少 8 位，而且字母和数字都要有。

登录状态靠一个 cookie 维持，有效期 30 天，所以关掉浏览器再打开还在。

### 注册这块还没做的

邮箱验证码还没做，等有发信通道了再加。所以现在只要有邮箱和密码就能注册，这个邮箱是不是真的归你，暂时不验。

找回密码、第三方登录、改邮箱，都还没做。

## 登录和退出

登录页 /login 上有邮箱和密码两个框，加一个登录按钮。填对了进工作台。

密码错和邮箱不存在，提示的是同一句话，"邮箱或者密码不对。"。不告诉人到底是哪个错，免得被人拿来试探哪些邮箱注册过。这两种情况后端花的时间也做得差不多，不然光看响应快慢也能猜。

同一个邮箱连着错，会被挡住一阵子。规则是 15 分钟里错满 5 次就锁住。锁住期间就算密码是对的也进不来，过了这 15 分钟自动能再试。登录成功会把这个邮箱的失败记录清掉。

已经有登录状态的人打开登录页或者注册页，会被直接送回工作台，不用再登一次。

工作台上有退出按钮。点完回登录页，而且那个登录状态在服务端立刻作废，手里存着旧 cookie 的人再拿来用也不认了。只清浏览器里的 cookie 是不够的，那样拦不住存了旧令牌的人。

没登录的人打开工作台，会被送到登录页，并且记住他本来想去哪，登完直接回那一页。

登录后要回的那一页只认本站地址。别人塞个站外网址进来会被换成工作台，不拿这里当跳板。地址栏里那种 `//evil.com`、`https://evil.com`、编码过的写法都试过，都挡住了。

这些判断都在中间件里做，它会真的去问一下后端这个会话还有效没有，不是只看 cookie 在不在。所以会话过期以后再打开，会被正常引导到登录页，不会来回打转。

## 余额和账本

每个账号有一个自己的钱包，工作台上能看到余额，新账号是 0。工作台上有个入口点到余额明细页 /wallet。

余额不是一个能直接改的数字。数据库里根本没有余额这个字段可以改，余额是把账本里的分录加出来的。想让余额变，只能写一条记录。

每条记录都写清三件事：什么时候、变了多少、为什么变。明细页上就是按这个显示。

这样做的直接好处是余额和记录永远对得上，因为本来就是同一个东西，不存在两边分别存一份然后对不上的情况。

### 改余额的规矩

这条规矩是定给以后用的，写在说明里，也落在代码和数据库上。

以后不管哪个功能要动余额，都必须写一条账本记录，不许绕过记录直接改数字。

代码这边，改余额只有一个入口，就是 apps/api/src/wallet/ledger.ts 里的 postLedgerEntry。别的代码想加钱扣钱都调它，不要自己写 SQL 去插或者去改。

数据库那边，就算有人绕过代码直接写库，也过不了两关。一是压根没有余额字段可以改，二是扣钱扣成负数会被触发器拦下来。

### 几个保底

余额扣不成负数。钱不够的时候是数据库那一层直接拒绝，不是只在应用里判断一下，所以从哪儿写进来都拦得住。这一层还先把钱包锁住，免得两个请求同时通过检查。

同一件事重复提交只算一次。每笔记录带一个幂等键，重复的键被唯一约束挡住。网络重试把同一个请求发两遍，钱也只动一次。

账本记录不许删也不许改。分录和事务这两张表上的外键都是 RESTRICT，想删会先被拦住。

### 查余额对不对

```
make check-balance
```

这个会把该查的查一遍。有没有余额变成负数的钱包，有没有账号漏了钱包，有没有光有事务却没有分录的脏数据，有没有重复的幂等键，还有每个钱包的余额换条路重算一遍是不是还一样。

全对就回一句"余额和记录一致，没发现问题"。有问题会列出来，并以非零退出。

### 这块还没做的

充值、支付、退款、赠送、返利、兑换码，都没做。

冻结、结算、释放这三件事也没做，按你说的，等有花钱的动作那一轮再一起做。所以现在账本里只有手工加的记录，还没有任何花钱的地方。

## 开始之前

本机要装 Docker Desktop，并且要开着。

## 怎么起

进到本目录，敲一条命令。

```
make up
```

第一次跑会拉镜像、编译代码，要等几分钟。跑完之后三块应用和三个基础设施都起来了。

起来之后看状态。

```
make ps
```

想跟日志就敲。

```
make logs
```

想把能自动查的一次查完，敲这个。每项打通过或者失败，最后汇总。

```
make verify
```

## 怎么停

```
make down
```

三块应用和三个基础设施全停掉，容器删掉。数据还在，下次起来数据不会丢。

## 怎么清空重来

```
make clean
```

这个跟 down 的区别是，它会把数据卷一起删掉。数据库、队列、文件存储里的东西全部清空，回到全新状态。

下次再 `make up`，就是一个干干净净的新环境。

## 开发测试线上三套怎么切换

三套环境用三个不同的项目名，容器和数据卷完全隔开，互不影响。用 make clean ENV=test 只会清掉测试环境的东西，碰不到开发环境。

要注意的是，三套默认用同一组端口，所以同一时间只能跑一套。换环境之前先把当前的停掉。

```
make down
make up ENV=test
```

开发环境，默认就是它。

```
make up
```

测试环境。

```
make up ENV=test
```

线上环境。

```
make up ENV=prod
```

停的时候也要带上对应的 ENV。

```
make down ENV=test
```

三套的差别是这样的。

开发环境把应用端口和三个基础设施的端口都开到本机，方便直接连数据库、连队列、开 MinIO 控制台看文件。

测试环境和线上环境只开应用端口，三个基础设施留在容器内网，从外面连不进去。

线上环境所有服务都配了 always 重启。

三套的配置分别写在 docker-compose.dev.yml、docker-compose.test.yml、docker-compose.prod.yml 里，公共部分在 docker-compose.yml。

环境变量也是三份，分别是 .env.dev、.env.test、.env.prod。这三个文件不进仓库。仓库里只有模板 .env.example。

配置文件的规矩不一样。开发环境缺了会自动从模板复制一份出来，图个方便。测试和线上缺了就直接停下报错，告诉你缺哪一份，不会拿占位值糊弄过去。这两套的配置要自己创建，密码换成真实值。

## 怎么确认真的起来了

最省事的是跑这一条命令，它把能自动查的都查一遍，每项打通过或者失败，最后汇总，有失败就以非零退出码结束。

```
make verify
```

下面是逐项手动查的办法，每一步都实际敲过。

### 一、看容器

```
make ps
```

六个服务都应该是 running 或者 healthy。postgres、redis、minio 三个会显示 healthy。

### 二、看网站

浏览器打开 http://localhost:3000

能看到一个写着"电商作图"的页面。不白屏，不出错误页。

### 三、看服务器活着没

```
make health
```

或者直接敲。

```
curl http://localhost:3002/health
```

会返回一段 JSON，status 是 ok。

三个依赖里只要有一个连不上，这个接口就直接回 503，不是把返回内容里的字样改一改。所以敲命令的人看状态码就知道成没成，前面加 -f 的话 curl 自己就会报错退出。

接口还有时间上限。任何一项卡住不回应，三秒内就判失败返回，不会一直挂在那。

### 四、确认数据库、队列、文件存储真的接上了

先看健康检查接口的返回。

```
curl http://localhost:3002/health
```

返回里有 checks 这一段，database、queue、storage 三个都应该是 ok。

这个 ok 不是写死的，是服务器每次请求都真的去连一遍数据库、ping 一下队列、列一下文件存储的桶，连上了才回 ok。任何一项连不上，整个接口回 503。

自己验一遍也简单，把数据库停掉再看这个接口。

```
docker stop dianshangzuotu-dev-postgres-1
make health
```

make health 会直接报错，不是打个 ok 出来。看完记得起回来。

```
docker start dianshangzuotu-dev-postgres-1
```

然后可以自己在外面再验一遍，绕过应用，直接连基础设施。

连数据库。

```
docker exec dianshangzuotu-dev-postgres-1 psql -U dianshangzuotu -d dianshangzuotu -c 'select 1'
```

能查出结果就说明数据库真的在跑。

连队列。

```
docker exec dianshangzuotu-dev-redis-1 redis-cli ping
```

回 PONG 就说明队列真的在跑。

看文件存储。

浏览器打开 http://localhost:9001 ，这是 MinIO 的控制台。用 .env.dev 里的 MINIO_ACCESS_KEY 和 MINIO_SECRET_KEY 登录，用户名是 localdevaccess，密码是 localdevsecret。

登录进去能看到一个叫 assets 的桶。这个桶是 api 启动的时候自动建好的，说明应用真的连上存储了。

### 五、确认 worker 在待命

```
docker compose -p dianshangzuotu-dev -f docker-compose.yml -f docker-compose.dev.yml --env-file .env.dev logs worker
```

日志里能看到 database connected、queue connected、storage connected，最后是 ready, waiting on queue "default"。

它连着队列在等任务，这轮不给它派活。

### 六、确认停得干净

```
make down
```

然后再敲。

```
docker ps -a
```

列表里找不到任何名字带 dianshangzuotu 的容器，说明停干净了，没有偷偷留着的。

## 镜像版本和运行权限

编排文件里的镜像版本全部钉到具体版本号，没有 latest 这种会漂的写法。postgres 用 16.15-alpine，redis 用 7.4.11-alpine，minio 用 RELEASE.2025-09-07T16-13-09Z，构建用的 node 用 22.23.2-alpine。

六个容器里跑服务的进程都不是 root。

网站、服务器、干活进程这三个是我们自己构建的镜像，里面建了个 uid 1001 的普通用户来跑。

postgres 和 redis 的官方镜像本来就会降权，跑服务的分别是 postgres 用户和 redis 用户。

minio 的官方镜像默认用 root，我们在启动命令里先把数据目录属主改成 1000，再降权成 1000 执行。

make verify 的最后一项就是查这个，六个容器挨个看 PID 1 的实际 UID。

## 队列密码

队列的密码两边永远是同一个来源，就是 .env 里的 REDIS_PASSWORD。

这个值不为空的时候，队列启动时就带上密码，应用也用这个密码去连。

这个值为空的时候，队列不设密码，应用也不带密码去连。

所以不会出现应用带着密码去连一个没设密码的队列这种情况。

想给开发环境加上密码，改 .env.dev 里的 REDIS_PASSWORD，然后 make clean 再 make up。

## 代码和密钥

代码里没有硬编码任何密钥或密码。数据库密码、MinIO 密码这些全部通过环境变量传进去，代码只读环境变量。

.env.example 里填的是本地开发用的占位值，不是任何真实系统的凭据。.env.dev 是 make 自动从模板复制出来的，也在 .gitignore 里，不会进仓库。

测试和线上环境必须换成真实值。

## 端口占用

开发环境会用这些本机端口。

3000 网站
3002 服务器
5434 数据库
6380 队列
9000 文件存储接口
9001 文件存储控制台

这台机器上本来就有别的项目在跑，占了 3001、5432、6379，所以这几个端口故意错开用了。

换一台没冲突的机器，想改回 3001、5432、6379 也可以，改 .env.dev 里对应的值就行，容器里面用的还是标准端口，不受影响。
